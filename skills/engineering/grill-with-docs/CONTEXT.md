# 说话方式

约定这个技能在当面说话和写术语表时，怎样把一个概念说清楚。

## Language

**人话**:
听的人不用先懂项目黑话，也能知道这个东西是什么的一句日常说法。
场景：客人已经点完，单子开了，钱还没扣成功。把这句话收成「已创建但尚未成功收款的订单」，就不再是人话。

**短场景**:
紧跟在人话后面的两三句话，里面有具体的人、具体的事和结果，用来标明哪些情况算、哪些不算。
场景：客人点了一份套餐，银行卡被拒，厨房还没做，单子留着等他换卡。菜已经开始做了，就不算「待支付订单」。这一个场景只讲这一件事。

**术语条目**:
术语表里的一个概念。先写一句人话，再写一个短场景，名字放在条目标题上。不写这东西在系统里怎么做。
场景：「待支付订单」这一条先说客人点完但钱没扣成，再写银行卡被拒、厨房还没做。条目里不出现数据库字段或接口。

**分叉**:
同一个说法有两种理解，而且这两种理解会让下一步的做法不一样。只有碰到分叉，才停下来起一个短名字。
场景：客人点了一份套餐，卡没付成。银行直接拒绝就作废、扣款超时就留着再试，这是分叉。两种情况都作废，就不是分叉，用人话确认后继续问下一件事。

**理由**:
给出建议时补的一句，说清选这个会怎样、另一个会怎样。
场景：建议把被拒的套餐单留着等客人换卡。厨房还没做，留着损失小；直接作废，客人还想吃也得重新点。这句话只出现在当面说话里，不写进术语条目。

**这次改动**:
这次要做的事，加上和它有关系、会被它碰到的地方。没有这层关系的地方不在里面。没被点名，本身不表示它在外面。
场景：这次要改的是结账时卡被拒就取消订单。退款和这次取消有关系，产品又没写清钱已经扣成要不要退，所以要问。厨房小票的字体和这次取消没有关系，不问。按钮用红还是灰也不改变这次取消，不问。

**确认**:
产品或业务已经说过的话，技能用一句日常的话复述出来，问听得对不对。同一句原话只问一次。
场景：产品写了「卡被拒就取消订单，不要重试」。技能只问「我听到的是卡被拒就整单取消、不重试，对吗？」它不再问取消是整单还是只取消一道菜，也不再说这和现在的做法相反、所以需求定不下来。

**对话**:
技能当面跟用户说话。先一句人话，再一个短场景，再一句理由。只有碰到分叉时，才在理由之后给出短名字，并问这个名字能不能用。
场景：用户说卡被拒或者扣款超时都把单子作废。技能说完「钱没扣成，单子作废」、套餐被拒的场景、以及为什么下一步这样建议，就继续问下一件事，不起两个名字。若银行拒绝是作废、超时是留着再试，才问要不要分开叫。开口就问「你是指 Order 还是 Checkout」，不算一次合格的对话。

## Relationships

- 一条 **术语条目** 含有一句 **人话** 和一个 **短场景**
- 一次 **对话** 先说 **人话** 和 **短场景**，然后给一句 **理由**
- **理由** 不写进 **术语条目**
- 只有 **分叉** 才让这次 **对话** 新增一条 **术语条目**
- 产品或业务的原话已经进入这次 **对话** 之后，技能只再问一次 **确认**
- **确认** 不新增 **术语条目**
- 一次 **对话** 只问和 **这次改动** 有关系的事；需求已经清楚、影响也能确定的，不再问

## Example dialogue

> **用户：**「卡被拒或者扣款超时，都把单子作废。」
> **技能：**「钱没扣成，不管是银行拒绝还是等了很久没结果，单子都作废。比如客人点了套餐，厨房还没做，这两种情况单子都直接取消。后来钱如果又扣成了，我建议退给他。餐没做成还收钱，客人会来要，不退就要专门处理投诉。」
>
> **用户：**「银行拒绝就作废，超时就留着再试一次。」
> **技能：**「同样是钱没扣成，两种结果不一样。比如客人点了套餐，银行拒绝时单子取消，扣款一直转圈时单子还留着。留着再试的那种，我建议叫待支付订单。厨房还没做，留着换卡损失小；直接作废，客人还想吃也得重新点。你用这个名字可以吗？」
>
> **用户：**「产品已经说了：卡被拒就取消订单，不要重试。」
> **技能：**「我听到的是卡被拒就整单取消、不重试。对吗？」

## Flagged ambiguities

- 「精炼」曾同时指「术语表写短」和「开口就用黑话」。已分开：短名字可以留在条目标题上；当面说话必须先是人话和短场景。
- 「性能」曾被拿来问术语表变长会不会变慢。这里指模型每次读整份术语表的字数，以及它能不能按场景把词用对。软件本身的运行速度不在这个词里。
